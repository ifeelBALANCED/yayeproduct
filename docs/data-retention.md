## 1. Що зберігається

| Таблиця             | Зміст                                                                                                                                                  | Чи є особисті дані                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `users`             | Анонімний UUID, `age_band`, `locale`, `jurisdiction`, `parental_consent_status`                                                                        | Мінімально: вік-діапазон (не ім'я, не email). Не ідентифікує особу напряму.          |
| `sessions`          | UUID сесії, FK на `users`, `started_at`, `ended_at`, `theme`, `end_reason`                                                                             | Опосередковано — через зв'язок з `users`.                                            |
| `messages`          | UUID, `session_id`, `role` (user/assistant), `content`, `prompt_version`, `created_at`                                                                 | Так: вільний текст користувача може містити особисті дані.                           |
| `crisis_events`     | UUID, `session_id`, `user_id`, `severity`, `detection_method`, `jurisdiction`, `review_at`, `review_by`, `review_notes`                                | Так: особливо чутливі (ст. 9 GDPR — дані про здоров'я у контексті психічного стану). |
| `booking_requests`  | UUID, `specialist_id`, `session_type`, `user_name`, `contact_preferred`, `contact_value`, `user_age_band`, `topic`, `consent_offer`, `consent_contact` | Так: ім'я, контакт (email або telegram), тема — ідентифікуючі дані.                  |
| `exercise_feedback` | UUID, `session_id`, `exercise_id`, `rating`, `completed`, `created_at`                                                                                 | Опосередковано — через `session_id`.                                                 |
| `consent_log`       | UUID, `user_id`, `consent_type`, `granted`, `granted_at`, `revoked_at`                                                                                 | Так: фіксація згоди суб'єкта даних.                                                  |
| `specialists`       | UUID терапевта, `name`, `bio`, `photo_url`, `active`, `slug`                                                                                           | Так: публічний профіль спеціаліста.                                                  |
| `therapists`        | UUID (збігається з `auth.users`), `full_name`, `email`, `specialization`                                                                               | Так: облікові дані терапевта.                                                        |
| `referrals`         | UUID, `session_id`, `therapist_id`, `proposed_slots`, `status`, `urgency`                                                                              | Так: через зв'язок зі сесією і терапевтом.                                           |

## 2. Правова база

**Продукт є wellness-застосунком, не медичним.** Ст. 9 GDPR (спеціальні категорії) застосовується до `crisis_events` і `messages` — вільний текст про психічний стан підпадає під розширене трактування «даних про здоров'я» (Recital 35 GDPR).

| Таблиця / дані                  | Правова основа                                                      | Стаття GDPR           |
| ------------------------------- | ------------------------------------------------------------------- | --------------------- |
| `users`, `sessions`, `messages` | Явна згода суб'єкта + виконання функції сервісу (контракт)          | Art. 6(1)(a), 6(1)(b) |
| `crisis_events`                 | Захист життєво важливих інтересів (imminent/high) + явна згода      | Art. 9(2)(c), 9(2)(a) |
| `booking_requests`              | Явна згода + виконання попереднього договору                        | Art. 6(1)(a), 6(1)(b) |
| `consent_log`                   | Відповідність правовому зобов'язанню (ст. 7 GDPR — доведення згоди) | Art. 6(1)(c)          |
| `exercise_feedback`             | Законний інтерес (покращення сервісу) + агрегація без ідентифікації | Art. 6(1)(f)          |

Hosting: Supabase Postgres, регіон `eu-central-1` (Frankfurt) — GDPR-compliant, дані не виходять за межі ЄС.

## 3. Строки зберігання (ПРОПОЗИЦІЯ)

> Строки нижче є пропозицією і НЕ виконуються автоматично — автоматичний retention job відсутній (борг, див. §4).

| Таблиця             | Строк зберігання                                                 | Обгрунтування                                                          |
| ------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `messages`          | 12 місяців з дати останньої активності сесії                     | Достатньо для continuity, мінімізація даних (Art. 5(1)(e))             |
| `sessions`          | 12 місяців з `ended_at` або `started_at` якщо не завершена       | Синхронно з `messages` (каскад)                                        |
| `users`             | 12 місяців з останньої активної сесії                            | Після видалення всіх сесій — user-row без змісту                       |
| `crisis_events`     | 24 місяці з `review_at` (або з `created_at` якщо не переглянуто) | Safety-review: мінімальний строк для аналізу ефективності safeguarding |
| `booking_requests`  | 6 місяців з дати створення                                       | Мінімально необхідний для support і спірних питань                     |
| `exercise_feedback` | 24 місяці                                                        | Агрегована аналітика ефективності вправ                                |
| `consent_log`       | На весь термін існування акаунту + 3 роки після видалення        | Юридичне зобов'язання зберігати докази згоди (Art. 7 GDPR)             |

## 4. Механізм видалення (erasure)

### Реалізовано

**`DELETE /api/sessions/[id]`** (Phase 2):

- Видаляє session-row.
- Каскад у БД (ON DELETE CASCADE) прибирає `messages` і `crisis_events`, прив'язані до сесії.
- `referrals.session_id` → ON DELETE SET NULL (referral-запис залишається для терапевта; `session_id` стає NULL).
- **Не видаляє** `users`-row — на одному користувачі може бути кілька сесій.

### Борг (не реалізовано)

| Борг                                                                              | Пріоритет |
| --------------------------------------------------------------------------------- | --------- |
| `DELETE /api/users/[id]` — повне GDPR erasure user + каскад всіх сесій            | Phase 4   |
| Automated retention job — cron що видаляє записи старші за строки §3              | Phase 4   |
| Erasure `booking_requests` після 6 міс (окремий flow, бо немає каскаду від users) | Phase 4   |
| Anonymization `crisis_events` після safety-review замість повного видалення       | Phase 4   |

**Поки automated job відсутній** — видалення відбувається лише за явним запитом користувача через `DELETE /api/sessions/[id]` або вручну DPO.
